# SiteSupervise Engineering Handbook

## 1. Project Vision & Business Domain
The SiteSupervise backend is built to ingest, process, and serve data generated by the **Tersus MVP S1 Handheld Scanner** (Data Producer). The backend acts as the bridge connecting physical construction scans with the digital project management ecosystem.

## 2. Technical Architecture
The backend follows Clean Architecture and Domain-Driven Design (DDD) principles.
- **Django Apps**: Isolated by domain (e.g., authentication, projects, scans).
- **Service Layer**: All business logic MUST be placed in a `services.py` within each app.
- **Thin Views**: Views should only handle HTTP request parsing, calling the appropriate service, and formatting the HTTP response.
- **Async Processing**: Celery and Redis handle long-running tasks like scan processing and report generation.
- **Storage Abstraction**: File storage must not assume local file systems in business logic; always use Django's storage API or custom abstractions for S3/Blob compatibility.

## 3. Folder Responsibilities
- `apps/`: Contains all business domain applications.
- `config/`: Global Django settings, root URL routing, and WSGI/ASGI entrypoints.
- `core/`: Cross-cutting domain logic, abstract base models, and shared utilities.
- `api/`: Global API configuration, versioning, and shared serializers.
- `docs/`: Markdown documentation and architectural decision records (ADRs).

## 4. Coding Standards
- **Python**: 3.13+
- **Style**: Enforced by `black` and `ruff`.
- **Typing**: Use standard Python type hints everywhere.
- **Docstrings**: Provide Google-style docstrings for all classes, methods, and complex functions.
- **PEP 8**: Adhere to PEP 8 standards automatically via pre-commit hooks.

## 5. API Conventions
- Use RESTful principles.
- All endpoints should be versioned (e.g., `/api/v1/...`).
- Input validation MUST be handled by DRF Serializers.
- Use generic views or ViewSets where applicable, but rely on the Service Layer for logic.
- Documentation must be auto-generated using `drf-spectacular` (Swagger/OpenAPI).

## 6. Service Layer & Model Rules
- **Models**: Fat models are discouraged. Models should only contain fields and basic property methods.
- **Services**: `services.py` holds the business logic. Example: `ScanService.process_scan_upload()`.
- **Selectors**: Read-only queries should optionally go into `selectors.py` to keep complex query logic reusable.

## 7. Testing Requirements
- Use `pytest` and `pytest-django`.
- All new features MUST be accompanied by unit tests.
- Target coverage is 85% minimum.
- Mock external services (e.g., S3, third-party APIs) during testing.

## 8. Git Workflow
- **Branch Naming**: `feature/ticket-name`, `bugfix/ticket-name`, `chore/task-name`.
- **Commit Messages**: Follow Conventional Commits format (e.g., `feat: add scan ingestion endpoint`).
- **Merge**: PRs require passing CI (linting + tests) and at least one review.

## 9. Definition of Done
- Code is written and adheres to standards.
- Tests are written and passing.
- Pre-commit hooks run successfully.
- API documentation (Swagger) reflects changes.
- Feature works seamlessly in a local Docker environment.

## 10. Security Requirements
- All endpoints must enforce authentication unless explicitly public.
- Use JWT for stateless auth.
- Role-Based Access Control (RBAC) must be implemented for sensitive actions.
- Never log sensitive data (passwords, tokens, PII).

## 11. AI Assistant Guidance
For future AI contributors:
- Always check this file and `README.md` before writing code.
- When adding a new feature, start with tests or update the `implementation_plan.md` first.
- Keep components modular. If a file gets too large, refactor into logical submodules.
- Do not introduce dependencies unless absolutely necessary.
